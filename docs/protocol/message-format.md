# Message Format (Version 1)

This document describes the implemented Phase 3 1-to-1 text-message foundation. It is a project-specific protocol composition and has not been independently audited.

## Wire Packet

The transport packet is deterministic JSON with exactly two top-level fields, in this order:

```json
{"envelope":{...},"transportMetadata":{"routeHint":null,"queueId":null,"ackId":null}}
```

The envelope contains exactly these fields, serialized in this order:

| Field | Purpose | Protected as AAD | Visibility |
| --- | --- | --- | --- |
| `protocolVersion` | Selects schema and cryptographic rules; currently `1` only. | Yes | Visible |
| `messageType` | Selects plaintext interpretation; currently `text` only. | Yes | Visible |
| `messageId` | UUID v4 identifier for retry identity and duplicate tracking. | Yes | Visible |
| `senderDeviceId` | Binds the session sender. | Yes | Visible |
| `recipientDeviceId` | Binds the intended recipient. | Yes | Visible |
| `sessionId` | Selects the established session and key context. | Yes | Visible |
| `sequenceNumber` | Monotonic per-direction replay state; starts at 1. | Yes | Visible |
| `keyEpoch` | Key-generation discriminator; only epoch `0` exists. | Yes | Visible |
| `nonce` | Base64-encoded 12-byte AES-GCM nonce. | Yes | Visible |
| `ciphertext` | Base64-encoded UTF-8 text ciphertext. | No, encrypted | Visible bytes |
| `authenticationTag` | Base64-encoded 16-byte AES-GCM tag. | No, generated by AEAD | Visible bytes |

No timestamp is used for replay protection. The envelope contains no identity private key, session root key, message key, password, recovery secret, or plaintext body.

`transportMetadata` is a separate, strictly parsed object with nullable `routeHint`, `queueId`, and `ackId` strings, each limited to 256 characters. It is not encrypted or authenticated by this protocol and must not influence message acceptance. The current implementation provides no relay or delivery behavior.

## Encryption And AAD

The primitive is AES-256-GCM from `cryptography` (`AesGcm.with256bits`). Plaintext is UTF-8 encoded and encrypted. The canonical JSON serialization of the first nine envelope fields, including the nonce, is supplied byte-for-byte as AEAD associated data. Ciphertext and tag are not included in the AAD. Transport metadata is excluded.

Changing any authenticated header field changes the AAD and causes authentication failure, or fails earlier during schema/session validation. The receiver decrypts into local memory only and returns plaintext only after AEAD authentication, UTF-8 decoding, and replay-state commit succeed.

## Key Hierarchy

1. The long-term Ed25519 identity key authenticates session establishment only. It is never used for message encryption.
2. Phase 2 establishes a 32-byte session root using ephemeral X25519 and HKDF-SHA256; the root is held by `SecureSessionStore` and, on mobile, FlutterSecureStorage.
3. A one-use 32-byte message key is derived for each message using HKDF-SHA256:

   - Input key material: the 32-byte session root.
   - Salt (`nonce` in the package API): UTF-8 bytes `echat.message-key.salt.v1`.
   - Info: UTF-8 canonical JSON, in fixed field order, containing `domain` = `echat.message-key.v1`, `sessionId`, `senderDeviceId`, `recipientDeviceId`, `messageId`, `sequence`, and `keyEpoch`.
   - Output length: 32 bytes.

Sender/recipient order separates directions. Session, UUID message ID, sequence, and epoch separate message keys. `keyEpoch` is fixed at zero; there is no rekey or ratchet implementation. `SessionService` lends a message key only to an encryption/decryption callback, destroys the key after the operation, and does not return it in an application model. Mutable plaintext and root-key copies are cleared where the language/library permits. A returned Dart `String` cannot be reliably zeroized.

## Nonce And Message ID

Each encryption calls the library’s `AesGcm.newNonce()`, which generates a fresh 12-byte nonce using a cryptographically secure RNG. Every message also has a distinct message key derived from its unique UUID v4, direction, and monotonically increasing sequence. This makes reuse of the same AEAD key across messages structurally unintended; nonce generation remains random, not sequence-derived. UUID v4 generation uses the UUID package’s `CryptoRNG` default.

The sender creates the message ID once when encrypting. A retry must resend the exact same serialized packet; it must not re-encrypt the same logical message as a new protocol operation. After successful authentication, the receiver rejects the same ID or any sequence not greater than its saved receive sequence.

## Serialization And Validation

Serialization uses Dart JSON encoding over insertion-ordered maps with no whitespace. Parsing requires exactly the known fields, correct types, canonical Base64, UUID v4 references, supported version/type/epoch, a 12-byte nonce, a 16-byte tag, and a canonical byte-for-byte reserialization match. Unknown fields and unknown versions are rejected. Duplicate JSON keys, alternate key order, extra whitespace, and noncanonical encodings therefore fail closed. Packet size is limited to 16 MiB and plaintext to 11 MiB.

Errors are converted to fixed protocol errors and do not include plaintext, keys, or attacker-controlled serialized contents.

## Sequence And Retry Rules

Send sequence is reserved atomically with per-session serialization and increases monotonically from 1. Receive handling holds the same session lock across direction/replay checks, key derivation, authentication/decryption, and replay-state commit. Failed authentication does not consume the message ID or sequence. Sequence gaps are accepted; older or equal sequence values are rejected, so out-of-order delivery is not supported. Replay state is stored with the session record. Concurrent duplicate deliveries can produce plaintext at most once.

The lock coordinates service instances in the same Dart isolate only. Cross-isolate or cross-process atomic replay-state updates are not implemented.

## Security Limitations

- The primitives are mature library implementations; the protocol composition is custom and unaudited.
- This does not implement a Double Ratchet, post-compromise security, or per-message forward secrecy.
- The transport sees device/session references, type, message ID, sequence, nonce, ciphertext length, tag, and optional transport metadata. It does not see message text.
- Transport metadata is intentionally unauthenticated and must not carry trust decisions.
- There is no relay, queue, persistent message database, UI, attachment, group, or multi-device support in this phase.
- This foundation is not production-approved and is not evidence of a complete secure messaging system.
